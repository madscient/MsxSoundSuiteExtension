## 統合する ROM の探し場所を呼ぶ側から渡す

Y8960 の `rom.py` は統合する4本を自身の `vendor/` と `../<repo>` の両方から
探し、両方在って中身が違えば止まっていた。Y8960 の作業機では兄弟の作業
リポジトリが常に並んでいるため、この検査が必ず発火して `vendor/` から組めな
かった。探し場所を呼ぶ側が環境変数で渡すことで候補が常に1つになり、この検査
そのものが要らなくなった。

依頼元は Y8960BasicExtension。依頼文書 `doc/prompt-msse-prebuilt-dir.md` は
4段が済んだので向こうで削除された（`e8f4471`）。

**外に出る値**：環境変数 `Y8960_PREBUILT_DIR`。4本のリポジトリが並んでいる
ディレクトリの絶対パス。読むのは Y8960 の `rom.py` と MSSE の `package.py`
だけなので、後から変えても波及先は2ファイル。

| | どちら | すること | 状態 |
|--:|---|---|---|
| 1 | MSSE | y8960 のステップに `Y8960_PREBUILT_DIR` を渡す | 済 `0319dcc` |
| 2 | Y8960 | `PREBUILT` に `rel` を足し、`rom.py` は渡された根＋`rel` だけを見る | 済 `d785baf` |
| 3 | MSSE | `package.py` の `check_cartridge_identity` を `rel` に切り替える | 済 |
| 4 | Y8960 | `paths` を消す | 済 `e8f4471` |

4段とも完了。`package.py` は `rel` を持たない `targets.py`（段2 より前の
gitlink）を名指しで拒否するので、ピンを戻した場合も黙っては通らない。

### 確度

- **確認済み** ―― `rom.py` が渡された値だけを見ること。`Y8960_PREBUILT_DIR`
  を外して `rom.py` を単体で走らせると、Y8960 自身の未初期化の `vendor/` を
  指して終了コード 1 で止まる。`build.py` 経由の通しビルドが通るのは、
  渡している値が効いているからだと言える
- **確認済み** ―― 通しのビルドとパッケージ化。5本すべてが組め、同一性検査は
  4バンクとも `vendor/` のビルド出力と一致した
- **確認済み** ―― 同一性検査が空振りでないこと。`mmbe_y8960.rom` の1バイトを
  反転させると `y8960bas` バンク #0 で拒否し、終了コード 1 になる。差分の位置
  （`0x0100`）まで出た。検査後に元へ戻し、sha256 の一致を確認済み
- **確認済み** ―― 二つの誤り経路。`rel` を持たない `targets.py` を渡した場合と、
  `rel` の指す像が無い場合に、それぞれの文面で `False` を返す
- **確認済み** ―― 段4（`e8f4471`）を取り込んでも出力が変わらないこと。組み直した
  `y8960bas.rom` が段3 の像と sha256 で一致し、パッケージ化も通る

## リリースノートの変更点を機械で集める

前回リリースからの変更点をリリースノートに載せるにあたり、**材料の収集だけ**を
機械化した（`tools/changelog.py`）。抽出と要約は人が書き、
`release.py --notes-file` で渡す。changelog は GitHub のリリースページにだけ
載せ、リポジトリに `CHANGELOG.md` は持たない。

**前提**：`vendor/` の5リポジトリが非公開であること。公開になれば下記 B の
危険が消えるので、判断は変わりうる。

**外に出る値**：`tools/changelog.py`、既定の出力先
`dist/changelog-material.md`、引数 `--since` / `--output`。読むのは人間だけで
他のスクリプトからは呼ばれないため、変えても波及先はこのファイルと
`docs/build-and-release.md` の1節。

### 飛ばせないようにする

ノートは「どの変更をすでに載せたか」の記録でもあるので、回を飛ばすと次の回で
前回ぶんと今回ぶんの区別が付かなくなる。文書の節が書き直されていると、告知済みの
変更も差分の上では新しい行として現れ、材料だけからは見分けられない。

そこで `release.py` に `notes_gate` を置いた。前回のタグから `docs/` か
サブモジュールのピンが動いているのに `--notes-file` も `--generate-notes` も
無ければ、定型文のままのリリースを拒否する。`--notes-file tools/release-notes.md`
と名指しすれば通る。止めているのは選ぶことではなく、忘れることである。

手順を文書に書くだけでは、読まなかった回に黙って通る。

### 見送った案

- **B：`release.py` から API を呼んで全自動にする** ―― 見送った。理由：生成物は
  リリースページ＝公開物で、材料には非公開リポジトリの ISSUE 番号や内部文書の
  名前が入っている。無検閲で公開へ抜ける経路を作ることになる。同じタグから
  同じノートが出ない点も、ずれたら止めるという他の検査の方針と合わない
- **C：ソース側のコミットに利用者向けの印を付ける（`User-facing:` トレーラ等）**
  ―― 今回は見送った。5リポジトリの `CLAUDE.md` 改訂と運用の徹底が要り、
  徹底されないと黙って抜ける。A の材料の質を上げる追加として後から乗せられる

### 確度

- **確認済み** ―― 前回タグが記録するサブモジュールのコミットから範囲を取れる
  こと。v0.2.0 と v0.2.1 の間で5本すべてから取れた（合計162コミット、うち
  `src/` を触るもの46）
- **確認済み** ―― `--since v0.2.0`、既定（最新タグ）、`--output -`、存在しない
  タグの4通りで走らせた。存在しないタグは終了コード 1 で止まる
- **未検証** ―― サブモジュールが未チェックアウトの場合と、前回タグのコミットが
  fetch されていない場合の分岐。書いたが再現させていない
- **確認済み** ―― 集めた材料からノートを書いて `--notes-file` で渡す流れ。
  v0.2.2 をこの流れで公開した
- **確認済み** ―― `notes_gate` が両方向に効くこと。v0.2.1 からの変更がある状態で
  拒否し、変更が無い状態では通す（`notes_gate` を直接呼んで確認）
- **推測** ―― パス限定の `git log -- src` は履歴の単純化でマージコミットを
  落とすことがある。根拠は git のパス限定ログの既定動作。落ちた場合もマージ
  された側のコミットが同じ範囲に残り、マージ自身は「その他」に出るので、
  材料としては欠けない

### OPLLEX の `@0`-`@63` は仕様変更ではなく修正

ノートの初稿は「0-63 がプリセット音色になりました」と、仕様変更として書いた。
利用者が「プリセット音色を選択できない不具合を修正しました」に書き換え、そちらが
正しい。v0.3.1 の `basic-reference.md` は FM の `@0`-`@63` を既にプリセットと
書いており、Y8960 の `plan.md` も「利用者の決定はユーザー音色表を `85` に
割り当てることで、OPLLEX の 0-63 の意味を変える決定ではない」としている。
食い違っていたのはコードのほうだった。

**修正扱いにすると、鳴り方が変わる事実が読み取れなくなる。** 旧コードは
`@1`-`@15` をチップ内蔵の音色として鳴らしていたので、そう書いた MML は
`@65`-`@79` に書き換えが要る。これをノートに足した。

**「直したもの」を1行から12件に広げた。** 初稿は `35cb6cb` の10件を
「仕様と食い違っていたのを直しました」の一行にまとめていたが、ポルタメントの
到達、フェード中のテンポ、リズムの音量、`Y` の保持など、どれも利用者が
気づける変化である。出典は Y8960 の `rom-discrepancies.md` の各項目と、
`plan.md` の課題「再生経路の食い違いを直す」の処理表。

**リズムモードの ch6-8 の F-Number は、音への影響を書かなかった。**
`rom-discrepancies.md` の B2 が、レジスタが `00` であることは確認済み、音への
影響は推測（鳴らしていない）としているため。ノートは「0 のままでした」で止めた。

段1 の報告で「通しのビルドは未検証。この作業機に zmac が無い」と書いた。
確かめたのは `ZMAC_EXE` が未設定であることと `zmac` が PATH に無いことの
2つだけで、5本すべての `tools/zbuild/build.py` が既定値として
`D:\Programs\8bit\zmac\zmac.exe` を持っていることは見ていなかった。実際には
環境変数を明示的に外してもビルドは通る（`env -u ZMAC_EXE` で確認）。

不在の証明には探し場所の列挙が要るが、走らせるだけなら1回で済む。
**「資源が無いので検証できない」と書く前に、まず走らせる。** 失敗したら
その失敗の内容を書けばよく、そのほうが「無い」より正確でもある。

代償は人間の往復1回と、根拠の無い「未検証」がレビュー順序を狂わせたこと。
確度はその順序のために書いている。

### AI 同士の取り決めの是非を人間に諮った

段1 の報告で、依頼文書が提示した環境変数名 `Y8960_PREBUILT_DIR` の可否を
人間に確認した。判断材料は Y8960 の `rom.py` と MSSE の `package.py` にしか
なく、両方を読んでいるのはこちらだけである。人間には判断手段が無い。

原因は「外から見える値を決める直前に一声かける」を、渡された値にも当てはめた
こと。あの規則が見ているのは自分が新しく決める値である。渡された取り決めは
自分で評価して、採るか異議を書くかを決める。

### 繰り返す手順

同一性検査（`package.py` の `check_cartridge_identity`）に手を入れたら、
通ることの確認だけでは足りない。**`vendor/` のいずれかの `*_y8960.rom` を
1バイト反転させ、拒否して終了コード 1 になることまで見る。** 反転前に
控えを取り、確認後に戻して sha256 の一致を見る。通るだけの観測は、検査が
空振りでも同じに見える。
